1. Motivazione: Amministrazione Remota e SSH

L'amministrazione di sistemi raramente avviene con accesso fisico diretto alle macchine. La stragrande maggioranza delle operazioni viene condotta da remoto, attraverso reti potenzialmente non fidate. Ciò introduce tre requisiti fondamentali di sicurezza:

  • Riservatezza: i dati trasmessi non devono essere leggibili da terzi.
  • Autenticazione dell'host: il client deve poter verificare di star effettivamente comunicando con il server atteso, e non con un impostore (attacco man-in-the-middle).
  • Autenticazione dell'utente: il server deve verificare l'identità di chi si connette.

Il protocollo SSH (Secure Shell) soddisfa tutti e tre questi requisiti, ed è oggi lo standard de facto per l'accesso remoto ai sistemi Unix-like.

2. Il Predecessore: TELNET

Prima di SSH, il protocollo dominante per l'accesso remoto era TELNET. TELNET soffriva di tre gravi lacune di sicurezza:

Requisito TELNET
Riservatezza ✗ — tutto in chiaro
Autenticazione host ✗ — assente
Autenticazione utente Solo passiva (password in chiaro)

L'assenza di cifratura implica che qualunque nodo di rete intermedio possa leggere l'intera sessione, incluse le credenziali. L'assenza di autenticazione dell'host espone l'utente ad attacchi di tipo man-in-the-middle: un avversario potrebbe impersonare il server e raccogliere le password inserite dall'utente ignaro.

3. Autenticazione a Chiave Pubblica

SSH supporta l'autenticazione basata su crittografia asimmetrica (a chiave pubblica). Il meccanismo si fonda sulla proprietà matematica per cui, dato un messaggio cifrato con la chiave privata, solo il possessore della corrispondente chiave pubblica può decifrarlo, e viceversa.

Il protocollo di autenticazione segue il paradigma PROVER / VERIFIER:

  1. Il VERIFIER (chi vuole verificare l'identità) genera un valore casuale (nonce) e lo cifra con la chiave pubblica del PROVER.
  2. Il PROVER (chi deve dimostrare la propria identità) decifra il nonce con la propria chiave privata e lo restituisce al VERIFIER.
  3. Il VERIFIER confronta il valore ricevuto con quello originale: se coincidono, il PROVER ha dimostrato di possedere la chiave privata corrispondente alla chiave pubblica dichiarata.

Questo schema è detto challenge-response con RSA ed è impiegato sia per l'autenticazione dell'host che per quella dell'utente (con chiave pubblica).

4. Passi della Connessione SSH

Una sessione SSH si stabilisce attraverso la seguente sequenza di fasi:

  1. Negoziazione del cifrario: client e server concordano gli algoritmi crittografici da utilizzare (cifratura simmetrica, hash, ecc.).
  2. Autenticazione dell'host: il server dimostra la propria identità presentando la propria chiave pubblica; il client verifica che corrisponda a quanto atteso.
  3. Canale cifrato: una volta autenticato l'host, viene stabilito un canale cifrato con la chiave di sessione negoziata.
  4. Negoziazione del metodo di autenticazione utente: client e server concordano come autenticare l'utente (password, chiave pubblica, ecc.).
  5. Autenticazione dell'utente: l'utente dimostra la propria identità con il metodo concordato.

Stabilite tutte queste fasi, la sessione interattiva (o l'esecuzione di un comando remoto) ha inizio.

5. Autenticazione dell'Host

Alla prima connessione verso un host, SSH non conosce la chiave pubblica del server. Il client deve quindi affidarsi a un meccanismo di verifica fuori banda (out-of-band): l'amministratore del server pubblica l'impronta digitale (fingerprint) della propria chiave pubblica attraverso un canale sicuro (documentazione interna, sito web istituzionale, ecc.), e l'utente la confronta manualmente con quanto presentato da SSH.

Una volta accettata, la chiave pubblica del server viene memorizzata nel file ~/.ssh/known_hosts del client. Nelle connessioni successive, SSH verifica automaticamente che la chiave presentata dal server corrisponda a quella memorizzata: se non corrisponde, emette un avviso di sicurezza che segnala una possibile compromissione.

6. Autenticazione dell'Utente

SSH supporta diversi metodi di autenticazione utente:

Autenticazione con password (passiva): l'utente inserisce la propria password, che viene trasmessa al server attraverso il canale cifrato. Questo metodo è detto passivo perché l'utente si limita a rivelare un segreto.

Autenticazione con chiave pubblica (attiva): il server verifica che l'utente possieda la chiave privata corrispondente a una delle chiavi pubbliche autorizzate, elencate nel file ~/.ssh/authorized_keys dell'account di destinazione. Il meccanismo è identico a quello descritto per l'autenticazione dell'host (challenge-response), ed è detto attivo perché l'utente dimostra il possesso del segreto senza rivelarlo.

Per impostazione predefinita, SSH utilizza il nome dell'utente locale come identità remota. È possibile specificare un utente diverso con la sintassi ssh utente@host.

7. Gestione delle Chiavi: ssh-keygen e ssh-copy-id

Generazione della coppia di chiavi

ssh-keygen -t rsa -b 2048

Il comando genera una coppia di chiavi RSA a 2048 bit, salvando: - la chiave privata in ~/.ssh/id_rsa (permessi 600, leggibile solo dal proprietario) - la chiave pubblica in ~/.ssh/id_rsa.pub

La chiave privata può essere protetta da una passphrase, che aggiunge un ulteriore livello di sicurezza: anche in caso di furto del file, l'attaccante non può utilizzare la chiave senza conoscere la passphrase.

Attenzione: i permessi della directory ~/.ssh devono essere restrittivi (700). Se i permessi sono troppo aperti, SSH rifiuta di utilizzare le chiavi presenti.

Installazione della chiave pubblica sul server remoto

Metodo automatico con ssh-copy-id:

ssh-copy-id [-i ~/.ssh/id_rsa.pub] utente@remoto

Metodo manuale con scp e aggiunta al file authorized_keys:

# Copia la chiave pubblica sul server remoto
scp ~/.ssh/id_rsa.pub utente@remoto:

# Sul server remoto, aggiunge la chiave alle autorizzate
cat id_rsa.pub >> ~/.ssh/authorized_keys

8. Esecuzione Remota di Comandi

SSH consente non solo sessioni interattive, ma anche l'esecuzione remota di singoli comandi:

ssh utente@host comando [argomenti...]

In questo caso, stdin, stdout e stderr del comando remoto vengono tunnelizzati attraverso il canale cifrato SSH: l'input locale viene inviato al processo remoto, e l'output (sia standard che di errore) viene restituito localmente. Questo meccanismo permette di integrare comandi remoti all'interno di pipeline locali.

# Esempio: lista dei file su un host remoto, ordinata localmente
ssh utente@host "ls /var/log" | sort

9. Vagrant: Riproducibilità e Portabilità

Vagrant è uno strumento per la creazione e la gestione di ambienti di sviluppo virtualizzati, progettato attorno a due obiettivi fondamentali:

  • Riproducibilità: l'ambiente viene descritto in modo dichiarativo in un file di testo (Vagrantfile), versionabile con git. Chiunque — o qualsiasi macchina CI/CD — può ricreare un ambiente identico a partire dalla stessa descrizione.
  • Portabilità: il Vagrantfile può essere condiviso nel repository del progetto. L'intero team di sviluppo lavora su ambienti identici, eliminando il problema "funziona sulla mia macchina".

10. Il Modello Vagrant

Vagrant si basa su un modello a componenti distinti:

Componente Descrizione
Box Immagine base della VM, distribuita sotto forma di file compresso.
VagrantCloud Repository pubblico (e privato) di box preconfezionati.
Vagrantfile File di configurazione Ruby che descrive la VM desiderata.
Provider Backend di virtualizzazione (VirtualBox, VMware, Hyper-V, …).
Provisioner Sistema di configurazione automatica della VM dopo la creazione (shell inline, Ansible, Puppet, …).

Il flusso tipico è: si scarica una box da VagrantCloud, la si descrive nel Vagrantfile insieme a rete, cartelle condivise, risorse hardware e provisioning, e si avvia la VM con vagrant up.

11. Il Vagrantfile

Il Vagrantfile è scritto in Ruby e segue la struttura seguente:

Vagrant.configure("2") do |config|

  # Box di partenza (da VagrantCloud)
  config.vm.box = "debian/bookworm64"

  # Configurazione di rete
  config.vm.network "private_network", ip: "192.168.33.10"
  config.vm.network "public_network"
  config.vm.network "forwarded_port", guest: 80, host: 8080

  # Cartelle condivise (host → guest)
  config.vm.synced_folder "code/", "/app/code"

  # Configurazione del provider (VirtualBox)
  config.vm.provider "virtualbox" do |vb|
    vb.memory = 2048
    vb.cpus   = 1
    vb.linked_clone = true
  end

  # Provisioner: script shell eseguito al primo avvio
  config.vm.provision "shell", inline: <<-SHELL
    apt-get update
    apt-get install -y apache2
    service apache2 start
  SHELL

end

Le sezioni principali sono:

  • vm.box: specifica la box da utilizzare; Vagrant la scarica automaticamente da VagrantCloud se non già presente localmente.
  • vm.network: configura le interfacce di rete (rete privata host-only, bridge sulla rete pubblica, o port forwarding).
  • vm.synced_folder: monta una directory dell'host all'interno del guest, mantenendo i file sincronizzati.
  • vm.provider: parametri specifici del backend di virtualizzazione (memoria, CPU, ecc.).
  • vm.provision: comandi o playbook eseguiti automaticamente al primo vagrant up per configurare il sistema.

12. Operazioni Vagrant

I comandi fondamentali per la gestione del ciclo di vita di una VM Vagrant sono:

Comando Descrizione
vagrant box add <nome> Scarica e installa una box da VagrantCloud (o da file locale).
vagrant init [box] Crea un Vagrantfile nella directory corrente.
vagrant up Crea e avvia la VM (esegue il provisioner al primo avvio).
vagrant status Mostra lo stato corrente della VM.
vagrant halt Spegne la VM (shutdown ordinato).
vagrant destroy Elimina definitivamente la VM e le sue risorse.

Una volta che il Vagrantfile è nella directory di progetto, tutti i comandi fanno riferimento implicitamente alla VM descritta in quel file.

13. Vagrant e SSH

Al momento del primo vagrant up, Vagrant genera automaticamente una coppia di chiavi SSH dedicate e configura la VM per accettare connessioni con quella chiave. Questo consente l'accesso SSH senza password alla VM.

Connessione interattiva

vagrant ssh

Equivale a connettersi come utente vagrant (che dispone di privilegi sudo senza password) alla VM in esecuzione.

Ispezione della configurazione SSH

vagrant ssh-config

Produce un output compatibile con il formato di ~/.ssh/config:

Host default
  HostName 127.0.0.1
  User vagrant
  Port 2222
  UserKnownHostsFile /dev/null
  StrictHostKeyChecking no
  PasswordAuthentication no
  IdentityFile /home/utente/.vagrant.d/boxes/.../private_key
  IdentitiesOnly yes
  LogLevel FATAL

Questo rivela l'equivalente esplicito del comando vagrant ssh:

ssh -p 2222 -i /home/utente/.vagrant.d/boxes/.../private_key vagrant@127.0.0.1

Vagrant utilizza il NAT con port forwarding: la porta 22 del guest è mappata sulla porta 2222 dell'host. Il parametro StrictHostKeyChecking no disabilita la verifica dell'host (accettabile in ambienti di sviluppo locali, ma da evitare in produzione).
